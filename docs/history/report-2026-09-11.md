# Report — why coachme v2 was not useful, and what v3 is

Written by Fable on 2026-09-11 after reading the whole repo (plan v2, the four phase
logs, KNOWN-ISSUES, DEPLOY, the code, the portfolio data). Every decision below is
made, not proposed: `plan.md` carries them as "already made", the prompt files
execute them. Anton's ask: *a tool that is better at helping me use Claude and Codex
to finish my repos and start making money with each one.*

## 1. Why the v2 build did not help

1. **It was never deployed.** Four phases (O1, O2, S1, S2) all ran against a local
   Postgres. No session ever had Vercel, Neon, GitHub-write or Anthropic
   credentials. Every feature is unproven in production, the phone has never
   received a push, and the twice-weekly scan has never run for real. The tool has
   produced zero output since it was built (2026-08-28).
2. **It was built to nag the human, not to do the work.** DESIGN.md diagnosed
   "execution avoidance on hPanel DB setup" and built a coaching state machine around
   it: priority ladder, anti-annoyance caps, shrink escalation, scope review, streaks.
   That is a lot of machinery whose only output is one push notification a day
   telling Anton to click through hPanel. Anton's actual leverage is delegation
   (Fable plans, Opus/Sonnet/Codex build). v2 gives the agents nothing to do.
3. **It stops at "launched".** `tier: revenue` is a label on 30 repos. Nothing
   records what the product sells, at what price, through which payment rail, to
   whom first, or how far each repo is from its first paying customer. A repo at
   95% with a database is still at 0 revenue; the tool cannot see that.
4. **The unit of work is wrong.** The only actionable object is a "DB session
   batch". 15 repos are `owner-setup-unclassified` and rank on a pessimistic guess;
   agent-drivable repos are shown read-only in the "Agent lane" with no way to start
   the agent. The tool knows those repos could be finished by a session and does
   nothing about it.
5. **The data is stale and incomplete.** The 53-repo baseline is from early August;
   the 2026-08-28 audit found 61 repos, four duplicate clones and a mislabelled
   repo. Without credentials the scan could not refresh any of it.

The code itself is good: the schema, query layer, scoring port, drift guard, runbook
generator, PWA and push are all tested and reusable. The problem is the product
definition, not the engineering. v3 keeps the foundation and changes what it is for.

## 2. What v3 is: a launch desk, not a coach

coachme becomes the place where each repo's **next unit of work exists as a
ready-to-run prompt**, gets **dispatched to Claude Code or Codex with one tap**, is
**tracked as a PR** until Anton merges it, and where every repo has a **money path**
with a measurable distance to first revenue.

Anton's daily interaction becomes: open the app, merge green PRs, tick "approve" on
the proposed work items, do the one owner step the app has prepped, and see which
repo is closest to earning. The agents do the rest, from the prompt files the app
wrote into their repos.

Three primitives, on top of the existing schema:

- **Launch stage** per repo: `building → deployable → live → sellable → marketed →
  earning`. "Done" now means earning, not launched.
- **Work item**: one bounded task toward the next stage, tagged `agent` (Claude
  Code or Codex, with the model to run it on) or `owner` (a human step with a
  runbook). Agent items carry a full prompt body. A Sonnet call proposes them from
  the repo's real state; Anton approves with a tick; the app dispatches by
  committing `prompts/coachme/<slug>.md` into the target repo and handing Anton the
  one-liner `Read prompts/coachme/<slug>.md in this repo and execute it.` — the same
  mechanism every build in this portfolio already uses, and it works identically
  for Claude Code and Codex.
- **Money path**: revenue model, price, payment rail, first-customer channel and a
  per-repo checklist generated from a playbook (SaaS / lead-gen / e-commerce /
  content, Paraguay / Sweden). The ranking that drives the home page becomes
  "distance to first revenue", not "percent done".

## 3. Decisions (locked; details in `plan.md` §1–§2)

| # | Decision |
|---|---|
| D-A | Reframe from coach to launch desk. The nudge engine stays as the delivery channel for a daily digest; it stops being the product. |
| D-B | Keep Next.js on Vercel + Neon. **Deploying is step P0 and it is mandatory** before any Sonnet phase is judged done. Anton may paste the tokens into a Sonnet session and have it deploy (DEPLOY.md's stated trade-off). |
| D-C | Launch stages are a `repos.stage` enum with six values; the scan and the generator may raise a stage only with evidence (live URL answers, a payment/lead page exists, a revenue date is set); Anton can set any stage by hand. |
| D-D | Work items are a table with a prompt body and a status machine (`proposed → approved → dispatched → pr_open → merged → done`, or `dropped`). Nothing is dispatched without an explicit tick. Proposals are estimates; ticks are facts — the same drift-guard principle as v2. |
| D-E | Dispatch = commit the prompt file to the target repo's default branch under `prompts/coachme/`, plus the one-liner shown in the UI. Optional second target: open a GitHub issue carrying the prompt. No per-repo GitHub Action install is required; both Claude Code and Codex are driven by the same file. |
| D-F | The GitHub token becomes a fine-grained PAT with Contents, Pull requests and Issues **write** on all repos of the account. The write client is allowed exactly three actions: create/update files under `prompts/coachme/`, create issues, squash-merge PRs whose head branch starts with `coachme/`, `claude/` or `codex/` and whose checks are green. No deletes, no force-pushes, no branch deletion, no repo settings — enforced in code and pinned by tests. |
| D-G | PR tracking rides on the existing scan cron: `listPulls` links PRs to work items by head branch `coachme/<slug>` or a `[coachme:<slug>]` marker in the title, and reads check status. Merging is an owner tap on the dashboard. |
| D-H | Ranking = distance to first revenue (stage gap, then existing leverage score). A `live` repo with a sellable path outranks a `building` repo at the same percent. The old invariant (95% infra beats early-stage) still holds inside a stage. |
| D-I | Money playbooks are content (`data/revenue-playbooks.json`), one per revenue model × market; per-repo tick state lives in a `revenue_checks` table. |
| D-J | The priority ladder gets two rungs on top: green PRs waiting for merge, then the owner item on the closest-to-money repo. The DB-session rung becomes a special case of the second. Caps and anti-annoyance rules are unchanged. Monday's nudge run also produces the weekly money report. Still two Vercel crons. |
| D-K | Models: the generator and the scan classifier call `claude-sonnet-5` via the API; the chat panel stays on Gemini Flash; Fable is used only in the planning conversations Anton opens himself. Build phases run on Opus (foundation) and Sonnet (everything else). |
| D-L | Codex is a first-class dispatch target: the prompt file header states branch and PR-title conventions so a Codex cloud task lands the same way a Claude Code session does. |
| D-M | Nothing built in v2 is deleted. Scope review, agent lane and the push card move off the home page to `/portfolio`; the home page becomes the digest. |
| D-N | The portfolio data is refreshed by a Sonnet phase running the real scan with credentials, reconciling the 61-repo audit (8 missing repos, 4 duplicate clones, 1 mislabel). |
