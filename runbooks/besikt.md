# Runbook — `besikt` (Neon PostgreSQL + Prisma)

> Generated by `src/runbook.js` from the repo's own stack. **Placeholders only —
> never paste a real password into this file.** Keep secrets in your password
> manager and in local `.env` files.
>
> `rapportverket` · 95% done · tier `revenue` · ~20 min

> **This one is not a Hostinger MySQL job.** It is Postgres, so the database lives at
> Neon and every schema command runs **from your own machine**. Hostinger's shared
> servers route IPv6 to Neon and fail every time — do not run these over Hostinger SSH.

## Step 1 — Create the Neon project (~3 min)

1. https://console.neon.tech → **New Project**.
2. Name it `besikt`, pick the region closest to the users.
3. Copy the **pooled** connection string it shows. It looks like
   `postgresql://<USER>:<PASTE_DB_PASSWORD>@<NEON_HOST>/<DB>?sslmode=require`.
4. Save it in your password manager as *"besikt — Neon"*. This is the only place
   the real string ever lives.

## Step 2 — Point your local checkout at it (~2 min)

```bash
cd besikt
npm ci
```

Create `.env` with:

```
DATABASE_URL=postgresql://<USER>:<PASTE_DB_PASSWORD>@<NEON_HOST>/<DB>?sslmode=require
NEXTAUTH_SECRET=<PASTE_NEXTAUTH_SECRET>
NEXTAUTH_URL=<PASTE_NEXTAUTH_URL>
ADMIN_EMAIL=<PASTE_ADMIN_EMAIL>
ADMIN_PASSWORD=<PASTE_ADMIN_PASSWORD>
```

`.env.example` lists 10 further variables (API keys, mail, providers).
None of them are needed to create the schema — leave them for the launch step.

> On Windows PowerShell, never write `.env` with `>` redirection — it produces UTF-16
> and the parser silently reads nothing. Use:
> `Set-Content -Path .env -Value 'DATABASE_URL=...' -Encoding utf8`

## Step 3 — Create the schema, from your machine (~5 min)

```bash
npm run db:push
```

```bash
npm run db:seed
```

> Run these locally. IPv4 to Neon works fine from a normal machine; from Hostinger's
> shell it resolves IPv6 and hangs. The **deployed app's** runtime connection is a
> different network path and does work — only the shell is affected.

## Step 4 — Give the deployed app its variables (~3 min)

hPanel → the `besikt` Node.js app → **Environment Variables**:

```
DATABASE_URL=<the same Neon string>
NEXTAUTH_SECRET=<PASTE_NEXTAUTH_SECRET>
NEXTAUTH_URL=<PASTE_NEXTAUTH_URL>
ADMIN_EMAIL=<PASTE_ADMIN_EMAIL>
ADMIN_PASSWORD=<PASTE_ADMIN_PASSWORD>
```

- Paste only the *value* into the value field. If a build error shows
  `input: 'DATABASE_URL=postgresql://...'`, the whole `KEY=value` string went into the value box.
- Any absolute-URL variable (`NEXTAUTH_URL` / `AUTH_URL`) must match the final domain —
  set it to the `*.hostingersite.com` URL first, update it after the custom domain is mapped.
- Env var changes need a **redeploy**, not just a restart.

## Step 5 — Verify (~2 min)

```bash
npm run build
```

Then open the deployed URL, log in, and create one real record. Rotate any seeded
default admin password immediately. If the record persists, `besikt` is unblocked —
tick it on the dashboard.

## If it goes wrong

| Symptom | Cause | Fix |
|---|---|---|
| Schema command hangs or times out | you ran it over Hostinger SSH (IPv6 to Neon) | run it from your own machine |
| `extension "…" is not available` | extension not enabled on the Neon branch | run `CREATE EXTENSION IF NOT EXISTS …` in Neon's SQL editor, then migrate again |
| Live site: generic "Application error" / `Digest:` | stale or malformed `DATABASE_URL` in hPanel | fix the value, then **redeploy** |
| `ERR_INVALID_URL`, error `input` contains `DATABASE_URL=` | key pasted into the value field | paste the raw value only |
| Auth redirects to the wrong host | `NEXTAUTH_URL` / `AUTH_URL` still on the old URL | update it and redeploy |
